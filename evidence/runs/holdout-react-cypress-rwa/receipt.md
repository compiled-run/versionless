## The finding

**Missing capability: non-UTF-8 module source decoding.**

webpack 4 decoded every module’s bytes leniently, so a dependency file stored in ISO-8859-1 reached the bundle with its bytes replaced rather than rejected. Vite 8’s bundler requires every module source to be valid UTF-8 and refuses to load one that is not. The frozen adapter has no capability covering byte-level source decoding, so the build stops.

- Exact demand: `UNLOADABLE_DEPENDENCY` loading `node_modules/faker/lib/locales/it/name/first_name.js` from `node_modules/faker/lib/locales/it/name/index.js`:5:27 — stream did not contain valid UTF-8
- Offending file: `node_modules/faker/lib/locales/it/name/first_name.js` (faker@5.5.3, 21980 bytes, sha256 `02a9f8a91945f0ed006e7b79efcfc7b9548f20e90042c5a0e84acaa6f654eb1d`), stored in ISO-8859-1, not UTF-8, 6 invalid UTF-8 bytes: 0xf9 at offset 5170 (`Esaù`), 0xe8 at offset 6973 (`Giosuè`), 0xe8 at offset 9233 (`Mosè`), 0xf2 at offset 9538 (`Nicolò`), 0xe8 at offset 9570 (`Noè`). Five of the six invalid bytes are listed; all six are accented characters in Italian given names.
- Reached from production application code: `src/utils/transactionUtils.ts` does `import faker from "faker";` — This is production application source, not test-only code, so faker 5.5.3 is genuinely in the browser module graph. faker’s locale index eagerly requires every locale file, so the Italian name list is pulled in whether or not the application uses that locale.
- Why this is not an adapter bug: The adapter’s five capabilities are about module semantics: tilde CSS specifiers, webpack’s sloppy-mode CommonJS wrapper, webpack’s Node core shim table, the ambient global identifier, and public directory replication. Source decoding sits below all of them, at the point where the bundler turns bytes into text. Nothing in the frozen composition is positioned to intervene there.
- Action taken: none. Recorded as a finding. No adapter change was proposed or executed.
